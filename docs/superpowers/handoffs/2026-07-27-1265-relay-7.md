## Fix plan — verified against current branch code

### BLOCKING-1(a): validate teamKey against catalog in `followTeam` — reject, don't null-and-continue

File: `packages/sports/src/sports-service.ts`, `followTeam` at line ~590 (search
`async followTeam`).

Currently only `competitionKey` is checked via `catalogEntry()`; `teamKey` passes through
unchecked into `repository.create`. The service already has everything needed to validate teams:
`getLeagueTeams(competitionKey)` (line ~178) calls `this.teamsFor(competitionKey, state)` and
returns `{ teams, degraded }` where `teams: SourceTeamRef[]` each carry a `teamKey` field (this is
the exact same team list the REST `GET /api/sports/leagues/:competitionKey/teams` route serves,
and the exact list `sourceTeamId` resolution already reads at sports-service.ts:295-298).

Fix `followTeam` to, when `input.teamKey` is non-null:
```ts
const teamKey = input.teamKey ?? null;
if (teamKey !== null) {
  const { teams } = await this.getLeagueTeams(input.competitionKey);
  if (!teams.some((team) => team.teamKey === teamKey)) {
    return { ok: false, error: `Unknown team: ${teamKey}` };
  }
}
```
then pass `teamKey` (not `input.teamKey ?? null` again) into `repository.create`.

Notes:
- `followTeam` is shared by both the REST route (`routes.ts` `POST /api/sports/follows`) and the
  assistant tool (`chat-tools.ts` → manifest `sports.followTeam`) — fixing it here closes the gap
  for both callers, which is correct (the REST route currently has the identical gap; QA's verdict
  assumed the route already validated teamKey and it doesn't — don't let that assumption block
  you, the fix is still exactly here).
- `teamsFor`/`getLeagueTeams` fails soft (returns `[]` + `state.degraded=true` on fetch failure,
  never throws) — so on an ESPN outage, ANY teamKey will be rejected as unknown. This is the
  correct fail-closed behavior for a security-tier auto-run write tool; do not add a
  degraded-bypass. If you're unsure, this is intentional per the coordinator's fail-closed framing
  — not a case to escalate.
- `unfollowTeam` (line ~608) does NOT need this — it has no outbound-URL sink (it only filters the
  actor's own existing rows by teamKey/competitionKey); QA's finding was specific to `followTeam`'s
  write-then-fetch path.

`sports.followTeam` and `sports.unfollowTeam` input schemas (4 field edits total: 2 tools ×
2 fields).

## Method note carried forward from Coordinator (apply to your own verification too)

`pgrep -f <pattern>` self-matches your own shell if the pattern appears in your own command line.
Before trusting a `/proc/<pid>/environ` read as evidence of another process's env, confirm the pid
via `/proc/<pid>/cwd` and `/proc/<pid>/cmdline`, not just that pgrep returned something. Relay-6
did this correctly (checked cmdline via `ps aux` before reading environ) — keep doing it that way,
not the pgrep-only shortcut.
